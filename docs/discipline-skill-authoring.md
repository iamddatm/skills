# 纪律型技能写作参考:形式匹配与防合理化

> 来源:译编自 [obra/superpowers](https://github.com/obra/superpowers) 的 `writing-skills` 技能中
> "Match the Form to the Failure" 与 "Bulletproofing Skills Against Rationalization" 两节(2026-08 译编,保留原文结构)。
>
> 适用场景:为本仓库编写或修改**纪律型技能**(grilling、ask-ui、verification 这类"agent 知道规则但会在压力下找借口绕过"的技能)时使用。
> 对技术型/参考型技能(dotnet-production-debug、wpf-stylet 等)不适用——它们失败于"不会用",而不是"找借口不用"。

## 先分类失败,再选写法

写任何约束之前,先判断基线失败属于哪一类。**同一种写法对一类失败有效,对另一类会实测起反作用。**

| 基线失败 | 正确形式 | 错误形式 |
|---|---|---|
| 明知规则,压力下仍跳过/违反 | 禁止令 + 合理化对照表 + 红旗清单(见下节) | 软性建议("倾向于…""考虑…") |
| 遵守了规则,但产出形状不对(prompt 臃肿、结论埋太深、复述规格) | **正面配方/契约**:写清输出"是什么"——由哪几部分构成、按什么顺序 | 禁止清单("不要复述""禁止叙述过程") |
| 在已产出的东西里漏掉某个必需元素 | **结构化**:在要填写的模板里加 REQUIRED 字段/槽位 | 模板旁边的散文提醒 |
| 行为应随条件变化 | **条件句锚定可观察判据**("若 brief 存在,则引用它") | 无条件规则 + 例外从句 |

**为什么"禁止"在塑造类问题上会反噬:** 当 agent 面临竞争性激励(比如"让 prompt 自包含")时,它会对 "不要做 X" 进行讨价还价。在 dispatch-prompt 约束的头对头措辞测试中,禁止组产出的不良内容明显多于配方组(两组分布完全分离),甚至比无约束对照组还差——你自己的场景请照此做微测试,但**默认不要选禁止式**。配方式没有讨价还价的空间:输出要么符合声明的形状,要么不符合。

**无论选哪种形式,都遵守以下规则:**

- **不写"看情况"从句。** "除非重要否则不要 X"会重开谈判——在同一个措辞测试里,往胜出配方上追加一条灵活从句,结果从稳定退化到噪声。真有例外,就把它写成独立的、锚定可观察判据的条件句。
- **豁免从句圈不住范围。** "此限制不适用于代码块"仍然会压制代码块。若输出的某部分必须豁免,就重构规则本身让它够不着那块,而不是加豁免句。

## 防合理化套件(Bulletproofing)

> 适用范围仅限纪律型失败:agent 明知规则却在压力下跳过。
> 产出形状错误、漏元素这类问题用禁止式会反噬,请改用上一章的形式匹配。

心理学背景:说服研究(Cialdini 2021;Meincke et al. 2025)表明确定性、承诺、权威等原则同样作用于 agent——理解这些能帮你系统化地应用下面的技术。

### 1. 逐条封死变通路径

不只写规则,要把已知的绕行方式一条条明令禁止:

不好:

```markdown
先写了代码再写测试?删掉。
```

好:

```markdown
先写了代码再写测试?删掉。重来。

**没有例外:**
- 不许"留着当参考"
- 不许"一边写测试一边改造它"
- 不许看它
- 删就是删
```

### 2. 掐断"精神 vs 字面"的辩论

在技能开头附近写上这句基础原则,一次性切断整类"我遵循的是规则精神"的合理化:

```markdown
**违反规则的字面含义,就是违反规则的精神。**
```

### 3. 建合理化对照表

从基线测试中收集 agent 实际说出的借口(原话),每条都进表:

```markdown
| 借口 | 现实 |
|--------|---------|
| "太简单了,不用测" | 简单代码照样坏。测一次 30 秒。 |
| "我之后再测" | 后写的测试只能证明"代码做了什么",不能证明"代码应该做什么"。 |
| "事后测试效果一样" | 目标相同≠约束相同——先写测试才有失败基线。 |
```

### 4. 建红旗清单

让 agent 在开始合理化时能自查:

```markdown
## 红旗——停下,重来

- 测试之前先有了代码
- "我手动验证过了"
- "事后测试能达到同样目的"
- "重要的是精神不是仪式"
- "这次情况特殊,因为……"

**出现任何一条都意味着:删掉代码,按 TDD 重来。**
```

### 5. 把违规前兆写进 description

在 description 里补上"即将违规时"的症状,让技能在agent快要失守的时刻被触发:

```yaml
description: 在实现任何功能或修复任何 bug、动手写实现代码之前使用
```
