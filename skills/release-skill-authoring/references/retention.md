# 保留策略与清理

发版是个反复动作：构建产物、清单归档、业务文件清单、服务端的历史包会一轮轮堆积。
不管的话几个月就是几十 GB。但「都删，只留最新」会**把发版链打断** —— 清理对象的安全边界
彼此不同，得分开定规则。

## 各类对象的边界

| 对象 | 位置 | 能删吗 | 为什么 |
|---|---|---|---|
| **当前更新包**（清单 `file` 指向的那份） | 服务端 | **绝对不能** | 删了所有客户端都更新不了 |
| **当前全量包**（清单 `fullFile` 指向的那份） | 服务端 | **绝对不能** | 停在旧基线的客户端唯一的升级路径，删了它们卡在「需要完整安装包」 |
| 历史版本的更新包 | 服务端 | 能删 | 更新包是**业务文件全集**，任何 ≥ `minVersion` 的客户端都能一步升到最新，中间版本没人需要 |
| 历史版本的全量包 | 服务端 | 能删 | 客户端要的是**当前基线**那份，不是更老的 |
| 历史清单归档 | 服务端 | 保留 N 份 | 体积小；用于审计与「这版当时发的是什么」 |
| 本地构建产物 `release/dist/` | 本地 | 保留最近 1 轮 | 已经上传了，留本地没用 |
| 本地清单历史 `release/history/` | 本地 | 保留 N 份 | 体积小 |
| **本地 `release/.payload-filelists/`** | 本地 | **至少 2 份** | 下一轮要拿上一份算**删除清单**。删了 → 被删掉的业务文件永远残留在客户端上，且无人察觉 |
| 本地 `release/.skill-backups/` | 本地 | 保留 N 份 | 优化发版技能时重渲染前留下的旧目录。是「改错了还能找回来」的保险，不是归档 —— 留 2 份就够 |
| 数据库备份 | 本地/远端 | **独立策略** | 不能跟着发版节奏删；保留期取决于你能接受回退多久 |

「本地」与「服务端」不是同一件事：本脚本只管本地。服务端的规则在文末。

## 顺序约束（最容易踩的一条）

```
生成清单 → 上传所有包 → 上传清单 → 线上体检通过 → 才允许清理
```

**提前清理 = 发不出去**。最常见的翻车姿势是「本地打包完成就顺手删 dist」—— 上传还没做。

## 命令

```bash
node scripts/engine/release-prune.mjs --config <repo>/release/release.config.json            # 演算，什么都不删
node scripts/engine/release-prune.mjs --config <repo>/release/release.config.json --apply    # 真删
```

**默认只演算。** 删除不可逆，而它又容易被顺手跑在「上传还没做完」的时刻 —— 所以真删要显式加 `--apply`。

它在**阶段 9 收尾**执行，是整条流程的最后一步：清单已上传、线上体检已通过之后。
删了什么、释放多少空间，必须打进发版报告（不做无声删除）。

## 配置

`release.config.json`：

```json
"release": {
  "retention": {
    "localDistVersions": 1,
    "localHistoryVersions": 5,
    "localPayloadFilelists": 2,
    "skillBackups": 2
  }
}
```

默认值偏保守（宁多留不误删）。用户说「只留最新」就把 `localDistVersions` 设成 1 ——
需要**反复迭代打包**的项目给它 2~3，免得下一轮改一行就得重跑全量构建。

`localPayloadFilelists` 会被脚本强制抬到 ≥ 2，配成 1 也不会照办：那不是偏好，是正确性下限。

## 服务端清理（本脚本不代劳）

服务端要删包得连上 CDN 源站，那涉及主机与凭据 —— 超出「发版脚本」的范围，而且删错是线上事故。
所以把**判据**给你，动作自己做：

```bash
# 1 先看清单当前指向哪两个包（这两个永远不能删）
curl -s https://dl.example.com/stable/manifest.json | grep -E '"(file|fullFile)"'

# 2 列出目录里所有包，人工比对后删掉不在上面的
ssh <host> 'ls -lt /var/www/dl.example.com/stable/p/ /var/www/dl.example.com/stable/f/'
```

判据（按优先级）：

- 清单 `file` / `fullFile` 指向的那两份 —— **不删**；
- 不在清单里、且比「当前版本往前 N 个版本」更老的 —— 可删；
- 拿不准就留着 —— 一个百兆全量包换一次「所有旧客户端卡住」，怎么算都值。

## 红线

- 不删服务端清单当前指向的更新包与全量包
- 不删 `release/.payload-filelists/` 的最近两份
- 不在「清单已上传 + 线上体检通过」之前清理
- 不把数据库备份并入清理范围（备份有自己的保留策略）
- 不做无声删除：删了什么、释放多少空间，必须打进发版报告
