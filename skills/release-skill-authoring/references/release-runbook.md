# 发版流程：九阶段

生成物的 `references/runbook.md` 就是按这份实例化出来的（把命令换成项目实际的）。
每阶段必须有：**命令 → 期望输出 → 门禁**。没有门禁的阶段等于没有阶段。

## 阶段表

| # | 阶段 | 做什么 | 门禁 |
|---|---|---|---|
| 0 | 预检 | **同步代码** + 分支纪律 + 发版锁 + 停机窗口 + DB 备份可用 + 工具链齐全 | 落后上游 → **拒绝继续** |
| 1 | 探测 | `release-changes.mjs` → `plan.json` | 🔴 把计划念给用户确认 |
| 2 | 兼容窗口 | 检查后端破坏性 API / 不可逆迁移 | 命中 → 必须上抬 `minVersion` 并附影响面 |
| 3 | 版本计算 | `release-version.mjs`（三源取大，严格大于线上） | 新版本必须严格大于上一版 |
| 4 | 数据库 | 生成 up/down → 备份 → 迁移 → 记录 `databaseVersion` | 不可逆项需显式开关 + 已验证备份 |
| 5 | 构建 | 前端 / 后端 / 客户端 | 产物存在且体积合理 |
| 6 | 打包 | 更新包（+删除清单）、全量包（条件）、安装包（条件） | 三重完整性断言 |
| 7 | 发布 | **先传所有包 → 最后传清单** | 幂等门禁（版本单调、禁重发） |
| 8 | 部署验收 | compose 更新 + 健康检查、前端翻指针、`release-verify.mjs` | 全部检查通过 |
| 9 | 收尾 | git tag（**每轮必打**）、更新说明归档、提交 state | tag 与清单版本一致 |

## 阶段 0：代码同步是硬门禁

```bash
git fetch origin
git status -sb                          # 首行带 [behind N] = 远端有新提交
git log --oneline HEAD..origin/<分支>    # 远端有、本地没有的提交
```

- **落后或有远端新提交** → 必须先合并再往下走。
  **带着旧代码发版 = 发出一个漏了改动的包**，而收到它的用户此后不会再收到那批改动
  （版本号已经前进），往往到用户投诉才发现；
- **合并纪律**：逐段合并双方意图，**绝不整文件覆盖队友**；合并后重跑受影响的测试；
  出现无法判断业务意图的冲突就停下问，别硬合；
- **有未提交改动**：先核对范围、备份本任务已测试的源码与上传清单，保留队友修改、
  不混入无关变更、**不自动 commit / push**；
- 门禁由 `release-changes.mjs` 实现，落后时直接拒绝（`--force-stale` 才放行并留警告）。

分支纪律：改动一律先落开发分支，主分支只接受**快进合并**，不在主分支上手工提交。

## 阶段 1：自动判定「这次要产出什么」

判定是**两段式**的：**git 说「可能变了」，内容指纹说「真的变了」**。

| 组件 | 检测 | 产出条件 |
|---|---|---|
| database / backend / frontend | `git diff --name-only <上版 tag>..HEAD` 按各自 glob 过滤 | 任一命中且指纹变化 |
| 客户端更新包 | 同上（业务 glob） | 客户端目录有变更 |
| 客户端全量包 | 运行时 glob + 新增目录检测 + `--force-full` | 见 `payload-rules.md` |
| 客户端安装包 | 派生：全量包需要时 | 与全量包同源 |
| 兜底 | 状态文件缺失 / `--reset` | **全部组件视为需要产出**（fail-closed） |

只看 git 会把「改了又改回来」也当成变更（白出一次全量包）；只看指纹则漏掉语义依赖。
两段都过才算变更。

## 阶段 3：版本计算

见 `versioning.md`。核心：**基准取「线上清单 / 本地状态 / 显式 `--base`」三者最大**，
保证严格大于线上 —— 否则客户端看不到更新。

## 阶段 6：更新说明（`notes`）

这是**用户唯一会看到的那几行字**（客户端更新卡片）。四条硬要求：

1. **发布前把拟好的说明摆给用户确认** —— 别自己拍板；
2. **不许省略**。省略后不少流程会拿当前 git 提交标题兜底，而那通常是「文档:…」这类
   不该给用户看的内容；
3. **按「用户能感知的变化」写**：新增了什么、修好了什么、体验上有什么不同。
   重构、内部改名、依赖升级、文档改动 **一律不写**；
4. **发布后读回线上，把这一版实际写进去的说明逐条回报给用户** —— 别说一句「已发布」就完事。

AI 草稿的生成方式：扫「上次发版 tag..HEAD」的提交区间，按上面的口径筛选改写。
生成脚本可以加 lint：**拒绝**内部 issue 号、文件路径、类名、`refactor` / `chore` / `docs` 这类词。

## 阶段 7：发布顺序

**先上传所有包，最后上传清单。** 清单是「最新是谁」的唯一指针，任何中间态都不该被客户端看到。
清单用临时名上传后再原子改名。

## 阶段 9：收尾

```bash
git add -A && git commit -m '<中文说明，不加任何署名>'
git fetch origin
git checkout main
git merge --ff-only origin/main     # 先让本地 main 跟上远端
git merge --ff-only dev             # 再快进；非快进 → 立刻停、问用户，别强合
git push origin main                # ⚠️ 对外动作，先要用户确认
git tag -a v<版本> -m '<说明>'
git push origin v<版本>              # ⚠️ 先要用户确认
git checkout dev
```

收尾后核一遍三者一致：`git log --oneline -1 main`、`-1 origin/main`、`git describe --tags`。

**push 与推标签前必须用户确认**；commit 中文、不加 AI 署名。

## 状态文件

`<repo>/release/release-state.json`（入库，团队共享，发布流程的唯一记忆）：

| 字段 | 用途 |
|---|---|
| `lastReleaseTag` / `lastReleaseCommit` | 下一轮变更检测的基准 |
| `versions.*` | 各组件版本；客户端的那个是版本号计算的三源之一 |
| `clientSeq` | 发布序号，单调递增 |
| `clientMinVersion` | 最低支持版本（兼容窗口下沿） |
| `clientFullBaseline` | 当前运行时基线 |
| `backendImageDigests` | 回滚用 |
| `artifacts[]` | 本次发布的包（路径、哈希、体积） |
| `componentFingerprints` | 各组件内容指纹，用于「真的变了吗」 |

**写入必须原子**（临时文件 + rename）：中途断电留下半截 JSON，会让下一轮退化成
「全部重建」甚至误判。

## 幂等与重跑

- **发版锁**（`release.lock`，含 pid）—— 防止两个发版流程同时跑；
- **版本单调**：拒绝写出 ≤ 上一版的版本号；
- **同版本禁重发**：要修内容就抬最后一段版本号；
- **清单只前进不后退**；
- 产物按版本命名，重跑覆盖自己那一版是安全的。

## 回滚剧本

| 组件 | 回滚方式 |
|---|---|
| 数据库 | 跑 down 脚本（**仅在可逆时**）；不可逆 → 恢复备份 |
| 后端 | 用 `release-state.json` 里的旧 digest 重新 `compose up`；源码级回滚用发版前的备份 tar |
| 前端 | 翻回上一个版本目录的指针 |
| 客户端 | **只能前滚**：用旧代码打更高版本号重发。不要改小版本号，客户端不会理会 |
| 清单 | 从 `history/` 取上一份（注意客户端只认更高 `seq`，回退清单通常无效，走前滚） |

回滚同样是**对外动作**，动手前先问用户。
